# Import Parsing Trust Sprint Plan

## Scope Guard
- Keep this sprint lean and reversible.
- Do not redesign the parser architecture.
- Do not remove recovery, replace recovery, or shift into CV Forge rewrite/redaction work.
- Preserve the current `structuredUpload -> StructuredUploadButton -> ProfileReviewCard -> import-recovery` workflow.
- Goal: shrink recovery volume materially so recovery becomes the exception, not the default import path.
- Reliability guardrail: do not degrade already-correct direct imports while reducing recovery volume.
- Tuning guardrail: prefer conservative routing; ambiguous content stays in recovery rather than being confidently injected into the wrong section.
- Verification target: reduce average recovery volume by roughly 30-50% on representative fixtures without increasing wrong direct placement.

## Implementation Defaults

### Shared resolver contract
- Reuse or extract one narrow canonical heading-resolution helper used by both active parser resolution and recovery classification.
- Keep it local to the parsing layer; do not introduce a broad new heading subsystem.
- The helper contract should normalize a heading/title into one canonical family or `null`, and be safe for both parser-side field-key derivation and recovery-side predicted section routing.

### Neutral residual target
- Replace the current unknown -> `summary` fallback with a neutral residual target.
- Lean default: add a minimal internal residual classification in recovery/types only, then materialize it through the existing safe plain-block path so it remains reassignable and cannot break schema/rendering.
- Do not turn residual into a new general editor workflow; it exists only to prevent unknown text from being mislabeled as summary.

## Root Cause Audit

### 1. Recovery classification is too strict for recognizable sections
- `buildImportRecoveryPayload()` sends every `low` item into recovery, and `low` is triggered not only by weak confidence but also by any severe flag.
- Current severe triggers are too aggressive for real CVs:
  - `weakSectionMatch` when a label matches but numeric confidence is missing
  - `unknownSection` defaulting unmatched content to `summary`
  - `ambiguousStructure` on common CV patterns such as subheadings plus bullets
  - `materialRewrite` from OCR cleanup noise
- Result: clearly mappable sections can still be held behind recovery.

### 2. Parser heading recognition is broader than recovery heading recognition
- `importRecovery.ts` has a much narrower alias map than parser heading detection.
- Common headings like `Professional Experience`, `Professional Summary`, `Career Summary`, `Education & Training`, `Key Skills`, `Technical Skills`, `Skill Set`, `Strengths`, and `Languages & Proficiency` are recognized upstream more often than they are recognized by recovery routing.
- Multilingual alias handling exists in parts of the parser but is not consistently applied through recovery and direct materialization.
- Result: a section can be parsed correctly enough to be useful, but still be downgraded during recovery classification.

### 3. Heuristic fallback produces weak field keys
- `hybridParser.ts` fallback currently derives `fieldKey` from the first word of the heading.
- That turns headings like `Professional Experience` into `professional` and `Technical Skills` into `technical`.
- Those weak keys then miss mapper buckets and recovery aliases, which inflates recovery or sends sections into generic buckets.

### 4. Segmentation is too coarse, so one uncertain subsection can poison a whole block
- `cvMapper.ts` layout rebuilding only has explicit heading coverage for a narrow core set.
- Unsupported headings fall through into the current section or the default summary path.
- `importRecovery.ts` then scores the entire mixed block as one item, so a single ambiguous subsection can force a large multi-topic block into recovery.

### 5. Some section families are still misrouted or not materialized directly
- `shared/headings.json`, `enhancedParser.ts`, and `llmPostProcessor.ts` currently contain cross-routing that treats `certifications` and some `projects` labels like `achievements` or `education`.
- `buildTypedSectionsFromNormalized()` currently materializes only profile, summary, experience, achievements, education, skills, and languages.
- `projects`, `certifications`, `hobbies`, `affiliations`, and `additional information` are not first-class direct output in the normalized-to-UI path.
- `buildTypedSectionsFromReviewerSections()` also collapses:
  - `projects` -> `experience`
  - `certifications` / `hobbies` / `publications` -> `achievements`
- Result: even correctly labeled content can still miss the intended destination unless the user fixes it through recovery.

### 6. Diagnostics exist as telemetry, but not as import-trust verification data
- Current telemetry logs recovery totals, but the import payload does not expose a compact routing breakdown that makes before/after verification easy.
- Result: it is hard to prove that recovery volume actually dropped and direct section placement improved.

### C. Reduce over-recovery in `importRecovery.ts`
1. Relax the current downgrade rules so recognizable sections do not become `low` purely because numeric confidence is absent.
2. Enforce precedence rules explicitly:
   - strong canonical heading match beats missing numeric confidence
   - OCR cleanup or cosmetic noise can penalize confidence but does not automatically force recovery
   - a single severe flag only forces `low` when it represents real structural ambiguity
   - unknown content never defaults to `summary`
3. Treat strong heading/title matches as importable unless additional signals show true ambiguity.
4. Replace the generic summary fallback with the neutral residual target and thread it safely through recovery types, payload serialization, materialization, and review UI.
5. Re-tune `ambiguousStructure` and OCR cleanup penalties so they only force recovery when they indicate real uncertainty, not merely normal CV formatting.
6. Keep recovery for:
   - unknown/unmappable fragments
   - mixed leftover text after safe splits
   - OCR junk/noise residues
   - genuinely low-confidence ambiguous blocks

### D. Improve segmentation without a full parser rewrite
1. Add a conservative second-pass split for oversized or mixed low-confidence sections in `my-app/convex/lib/parsing/importRecovery.ts`.
2. Split only when there are strong structural cues such as:
   - recognized subheadings
   - repeated uppercase/title-case section lines
   - strong date/header boundaries
   - bullet groups separated by real section cues
3. Apply anti-fragmentation rules:
   - do not split recognized header-body pairs
   - do not split title-date pairs
   - do not split bullet groups from the nearest recognized heading unless a stronger boundary appears
   - prefer fewer safe fragments over maximal fragmentation
4. Add a minimum fragment size threshold and merge undersized fragments into adjacent compatible content.
5. Cap split fan-out per source block to avoid explosion on noisy OCR text.
6. Score fragments independently after splitting.
7. Route medium/high-confidence safe fragments directly and keep only ambiguous residual fragments in recovery.
8. Prevent giant whole-CV or whole-section recovery blobs whenever smaller safe fragments can be extracted.

### E. Expand direct materialization for non-core sections

2. Add direct output support for:

3. Prioritize first-class direct handling for `Projects` and `Certifications`.

5. Reuse existing section factories and recovery materialization conventions where possible:

7. Do not over-structure weakly structured content in this sprint.

## Phase 3: `PERSONAL DOSSIER` Safety Audit

### Audit Question
- Determine whether `PERSONAL DOSSIER` can be safely promoted out of `BODY` on the active plain-PDF path without creating privacy, summary, profile, routing, or recovery side effects.

### Findings

#### Safest existing downstream bucket
1. `additional_information` — safest promoted destination.
   - Already exists as a block-backed text section in the active app path.
   - Is isolated from summary/profile inference.
   - Works in both direct materialization and recovery materialization.
2. `custom` — safe only as reviewed recovery residue, not as a promoted canonical bucket.
3. `details` — unsafe/incomplete because the active app path has no real standalone `details` raw-section destination.
4. `profile` — unsafe because it can pollute summary and contact/profile inference with personal-detail text.

#### Why `profile` is unsafe
- Python canonicalization treats `PROFILE` as summary source.
- App-side canonicalization also uses the first `profile` raw section as summary-adjacent input and place-of-birth extraction input.
- A dossier block typically contains DOB, gender, marital status, address, passport-like fields, and other private details that should not be promoted into summary.

#### Why `details` is not enough
- Python already has a `DETAILS` label family, but the active app path does not have a clean first-class downstream `details` family.
- In recovery/resolution logic, `details` tends to collapse toward profile/contact-like handling rather than a dedicated safe personal-details section.
- That makes `DETAILS` an unstable intermediary unless a second patch carries it to a safe destination.

#### Existing safe destination availability
- `additional_information` already exists downstream as a safe text-backed section.
- `profile` already exists downstream, but it is not safe for dossier material because of summary/profile heuristics.
- There is no standalone safe `details` bucket in the active end-to-end path.

### Current Recommendation
- Leave `PERSONAL DOSSIER` unpromoted for now unless we explicitly decide to auto-materialize it as `Additional Information`.
- Current residual review behavior is safer because it keeps private dossier content behind a user review gate instead of auto-persisting it into the document.

### Ranked Recommendation
1. Default recommendation: keep `PERSONAL DOSSIER` in residual review for now.
2. If we later choose to promote it, promote only to `additional_information`.
3. Do not promote it to `profile`.
4. Do not promote it to `details` unless `details` is also mapped end-to-end to a safe text-backed bucket.

### Smallest Safe Implementation Path If Promotion Is Chosen Later
- Map `PERSONAL DOSSIER` to `ADDITIONAL INFORMATION`, not to `PROFILE` or `DETAILS`.
- Minimal cross-layer path:
  1. Add `PERSONAL DOSSIER` to the active heading map in `cv_parser/canonicalize.py` with the label `ADDITIONAL INFORMATION`.
  2. Add `personal dossier` as an alias under `additional_information` in the shared heading resolver contract so recovery and raw-section materialization agree.
