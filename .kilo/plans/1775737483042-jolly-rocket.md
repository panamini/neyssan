### Current active-code behavior
- `derive_raw_sections_from_markdown_pages(...)` creates a `LANGUAGES` section only when:
  - a markdown heading resolves to `LANGUAGES`, or
  - a plain standalone line resolves to `LANGUAGES` and is followed by a markdown table
- `_select_family_scoped_ocr_raw_sections(...)` currently carries language content only when an OCR raw section is already labeled `LANGUAGES`
- `extract_language_markdown_table_region(...)` already knows how to isolate a parseable language table region from mixed content
- `build_language_entries(...)` already parses a carried `LANGUAGES` markdown table conservatively from the language-name column only

## Earliest confirmed / likely loss points

### Confirmed downstream loss
- The accepted downstream result already shows no canonical `LANGUAGES` block reaches `build_language_entries(...)`
- Therefore `sections.get("LANGUAGES", []) == []` at `cv_parser/canonicalize.py:2733`

### Likely earlier boundary from active code + fixture layout
- Because `LANGUAGE KNOWN` is likely present only as a table header row, `derive_raw_sections_from_markdown_pages(...)` has no standalone heading boundary to split out a `LANGUAGES` raw section
- In that case the language table remains attached to the preceding section content (most likely `ACHIEVEMENTS`, possibly another mixed section depending on OCR markdown ordering)
- When global OCR raw-section activation is `False`, `_select_family_scoped_ocr_raw_sections(...)` then drops the opportunity to recover the table because it only carries `label == "LANGUAGES"`

## Smallest safe patch once implementation is allowed
- Change only `cv_parser_service/main.py::_select_family_scoped_ocr_raw_sections`
- Keep the existing explicit `label == "LANGUAGES"` path intact
- Add a second, family-scoped fallback for `LANGUAGES` only when `use_ocr_raw_sections` is `False` and no explicit language block was already carried:
  - scan `ocr_raw_sections`
  - call `extract_language_markdown_table_region(content)` / `has_parseable_language_markdown_table(content)` on section content regardless of section label
  - if a parseable language table region is found, carry only that isolated region as `{ "label": "LANGUAGES", "content": region }`
  - do not carry surrounding mixed text
  - do not reinterpret the source section as `SKILLS`
- Do not change `derive_raw_sections_from_markdown_pages(...)` unless actual live markdown proves there is a standalone close-variant language heading line that current detection misses

## Why heading recovery is not the recommended first patch
- Active mappings already cover `LANGUAGE`, `LANGUAGES`, `LANGUAGE KNOWN`, `LANGUAGES KNOWN`, `LANGUES`, `IDIOMAS`
- If the target OCR path emits only a table header row and not a standalone heading line, more heading recovery does nothing
- The existing region extractor already solves the narrower problem at lower risk

## Why SKILLS stays out of scope
- The goal is only to recover a canonical `LANGUAGES` block so the existing language-table parser can run
- The proposed fallback extracts only a language-table region already recognized by `has_parseable_language_markdown_table(...)`
- No shared skills/languages parsing changes are needed
- No `SKILLS` classification, carry-through, or parser logic needs to widen
