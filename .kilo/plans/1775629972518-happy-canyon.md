# Low-Confidence Section Review Gate - Step 1 Plan

## Goal

Implement the smallest production-ready vertical slice of an import recovery layer in `my-app`, scoped explicitly as a low-confidence section review gate: low-confidence imported content is reviewed before it is committed into the final CV document, while high-confidence imports keep the current fast path.

This matches Step 7.1 as a trust-gateway initiative: the product should not rely only on better parsing, it should build a recovery UX around parsing.

## Repository Audit

### Active import path

1. `my-app/src/pages/CvForge.tsx`
   - Renders the active resume workspace.
2. `my-app/src/components/ProfileReviewCard.tsx`
   - Hosts the active import triggers.
   - Empty-state import path calls `importSectionsIntoFreshCv(...)`.
   - Existing-document import path calls `reorderSections(...)`.
   - Already contains an import warning/review UI pattern that can be reused.
3. `my-app/src/components/StructuredUploadButton.tsx`
   - Reads file/text input.
   - Calls Convex `structuredUpload`.
   - Immediately maps parser output into typed `CvSection[]` and applies it.
4. `my-app/convex/actions/structuredUpload.ts`
   - Active server entry point for structured import.
   - Calls external parser service (`/parse-cv` or OCR route), normalizes payload, returns diagnostics.
5. `my-app/convex/lib/parsing/hybridParser.ts`
   - Active parser orchestration.
   - Produces parsed sections with `fieldKey`, `content`, `confidence`, `warnings`, and parser `method`.
6. `my-app/convex/lib/parsing/cvMapper.ts`
   - Active section classification / canonical mapping layer.
   - Carries section confidence, source spans, metadata confidences, and experience diagnostics.
7. `my-app/src/utils/cv/mapping-utils.ts`
   - Builds typed editor `CvSection[]` from normalized parser output.
   - Current gap: confidence/diagnostic data is mostly dropped here.
8. `my-app/src/lib/normalize-cv.ts`
   - Normalizes/validates the final `CvDocument` and synthesizes representative blocks.
9. `my-app/src/contexts/CvLibraryContext.tsx`
   - `importCv(...)` is the final persistence gate for imported documents.

### Existing confidence/diagnostic signals

- `hybridParser.ts` already emits per-section numeric confidence.
- `cvMapper.ts` preserves confidence and diagnostics in intermediate structures.
- `structuredUpload.ts` already carries parser diagnostics and empty-result reasons.
- `src/lib/cv-import-signals.ts` performs post-import document-level trust checks, but only after content is already placed into the CV.

### Current gap

The active CvForge import flow applies mapped sections immediately. Low-confidence parser output is not intercepted before import, and the typed `CvSection[]` transformation drops most section-level confidence data.

### Scope / assumptions

- Target the active CvForge import path first: `ProfileReviewCard` + `StructuredUploadButton` + `structuredUpload`.
- Reuse the current inline review visual language instead of building a new full-screen workflow.
- Preserve high-confidence auto-import behavior.
- Step 1 scope is explicitly `low-confidence section recovery`, not broad import repair.
- Do not rewrite the parser.
- `my-app/docs/benchmark/5_executive_product_roadmap.md` exists but is currently empty, so implementation will follow the request in this chat rather than roadmap file content.
- DOCX is not wired through the active `StructuredUploadButton` path today; Step 1 should attach the recovery layer to the active pipeline first. If parser transport already accepts DOCX bytes, enable it opportunistically during implementation; otherwise leave DOCX transport expansion for follow-up.
- Parsed review state can remain transient for Step 1, but refresh/navigation loss is a known UX limitation to track for v2 if users complain.

### Step 1 explicitly improves vs does not improve

Improves immediately:

- obviously wrong section placement reaching the final CV
- silent parser failures with weak section confidence
- user trust through visible review of uncertain content

Does not yet improve:

- broken parser segmentation when the upstream parser already merged/split content incorrectly
- deep bullet reconstruction from highly malformed source text
- extraction quality from hard PDFs, layout-heavy resumes, or bad OCR beyond existing parser capabilities

This is acceptable for Step 1 because the review unit is still the parser's initial section/block segmentation.

### Alignment with Step 7.1

The current plan answers the roadmap step directly:

- `import normalization pass`: covered by existing `structuredUpload` normalization plus the new recovery shaping layer
- `glyph cleanup pass`: covered in cleanup/scoring utilities
- `duplicate text cleanup`: covered in cleanup/scoring utilities and severe duplicate flagging
- `bullet normalization`: covered in cleanup/scoring utilities
- `confidence scoring on imported blocks`: covered by recovery item model + scoring thresholds
- `review uncertain blocks screen before full document entry`: covered by the review gate before `importCv(...)` / `reorderSections(...)`
- `quick reassignment UI for uncertain content`: covered by review actions and dynamic target-section creation
- `obvious section repair flow`: covered by accept / reassign / ignore actions, plus `Import as-is` fallback

The only deliberate gap versus the broad wording of Step 7.1 is that Step 1 does not repair upstream segmentation mistakes; it repairs section assignment and visible uncertainty around parser output.

## Minimal Design

### 1) Introduce a focused import recovery model

Add a small shared model for recovery items, separate from the main `CvDocument` shape:

- `blockId`
- `rawText`
- `cleanedText`
- `predictedSection`
- `confidenceScore` (`high | medium | low`)
- `confidenceValue` (numeric passthrough when available)
- `issueFlags` (`glyphIssue`, `bulletIssue`, `duplicate`, `unknownSection`, `weakSectionMatch`, `ambiguousStructure`)
- `reviewStatus` (`pending | accepted | reassigned | ignored`)
- `sourceSectionTitle` / `sourceFieldKey` for traceability

Implementation preference:

- Add a dedicated type file such as `my-app/src/types/importRecovery.ts`.
- Persist accepted block metadata onto final blocks via `CvBlock.attributes.importRecovery`.
- Keep ignored items in transient review state; optionally store a lightweight session summary under passthrough metadata if needed.

This keeps the slice small and avoids a broad `CvDocument` schema redesign.

### 2) Add first-pass cleanup + scoring utilities

Add a utility module, likely shared or frontend-first depending on runtime fit, for:

- bullet normalization
- broken glyph replacement/stripping
- whitespace and repeated line-break cleanup
- duplicate text detection
- confidence banding (`high | medium | low`)
- review-item construction from parser sections

Scoring rules for the first slice:

- `low` if section confidence is weak, field key is missing/unknown, cleanup materially changes the text, bullets look malformed, text is duplicated, or structure is ambiguous.
- `medium` if section confidence is usable but not strong, or cleanup finds moderate noise.
- `high` otherwise.

Initial numeric cutoffs and flags:

- Base numeric confidence source: parser section `confidence` when present; if missing, start at `0.65` and let issue flags decide the band.
- `high`: `>= 0.8` and no severe issue flags.
- `medium`: `0.55 - 0.79`, or `>= 0.8` with one moderate issue.
- `low`: `< 0.55`, or any severe issue regardless of numeric score.

Initial severe issue flags that force `low`:

- `unknownSection`
- `weakSectionMatch`
- `ambiguousStructure`
- `duplicate`
- combined `glyphIssue` and `bulletIssue`
- cleanup materially rewrites the content, defined initially as either:
  - cleaned text length delta greater than `20%`, or
  - 3 or more broken glyph replacements, or
  - 2 or more bullet normalization repairs on the same item

Initial moderate issues that keep an item in `medium` unless the numeric score is already low:

- isolated `glyphIssue`
- isolated `bulletIssue`
- moderate whitespace/newline cleanup
- parser confidence present but under `0.8`

Tuning guardrail:

- Bias the first release toward not over-triggering review. Unknown/ambiguous/malformed items should be reviewed, but merely imperfect items should stay on the automatic path.

Recommended insertion point:

- Build recovery items from the parser section artifacts before `buildTypedSectionsFromNormalized(...)` erases confidence context.

### 3) Surface recovery payload from the active import pipeline

Preferred minimal path:

- Extend `my-app/convex/actions/structuredUpload.ts` to return a compact `recovery` payload alongside `normalized`, `strict`, and `diagnostics`.
- Source the recovery items from the already-available parsed/raw sections and parser diagnostics.

Why this is the best insertion point:

- It is the narrowest active choke point.
- It already sees parser diagnostics, OCR mode, salvage behavior, section confidences, and normalized output.
- It avoids coupling the UI to unstable internal parser payload shapes.

Fallback if server shaping proves too expensive:

- Build recovery items in `StructuredUploadButton.tsx` from returned normalized raw sections, but only if the required confidence/raw-section data is already present.

### 4) Gate low-confidence imports in the UI

Add a minimal review panel/component, likely mounted from `ProfileReviewCard.tsx`.

Behavior:

- If no low-confidence blocks exist: keep current behavior.
- If low-confidence blocks exist: do not call `importCv(...)` / `reorderSections(...)` yet.
- Show only low-confidence blocks.
- For each block allow:
  - accept suggested section
  - reassign to another canonical section
  - ignore
- After review completion, apply the decisions and continue the normal import.

Safety / UX constraints for Step 1:

- Always provide a no-review fallback: `Import as-is` and `Cancel` remain available if recovery payload exists but the user does not want to review, or if the review state fails.
- Add a hard cap on manual review items. If low-confidence block count exceeds `12`, show the first `12` items, summarize the remainder, and keep `Import as-is` / `Cancel` visible so the user is not trapped in a giant review wall.
- If the review state is lost by refresh/navigation, the upload is lost in Step 1; this is acceptable for now but should be recorded as a known v2 persistence gap.

Recommended UI reuse:

- Reuse the existing import review container pattern in `ProfileReviewCard.tsx`.
- Keep controls simple: text preview, section select, three actions, and a final continue/apply action.

Target UX flow:

- import
- normalize and score
- surface uncertain areas
- quick review
- continue into the editor

Example user-facing copy for Step 1:

- `We imported your resume. Review 3 uncertain sections before continuing.`
- `We're not sure where this paragraph belongs.`
- `We found unusual formatting in this section.`

### 5) Apply reviewed blocks into typed sections with metadata

After review:

- Merge accepted/reassigned low-confidence blocks into the typed section set.
- When reassigned into a canonical section that does not yet exist, create that typed section on demand using the same template-driven section generation rules already used elsewhere in the editor.
- Stamp final blocks with `attributes.importRecovery` metadata.
- Skip ignored blocks.
- Then proceed through the existing import path:
  - fresh CV -> `importSectionsIntoFreshCv(...)`
  - existing CV -> `reorderSections(...)`
  - final persistence remains in `CvLibraryContext.importCv(...)`

This preserves current normalization and persistence behavior.

## Implementation Sequence

1. Add the recovery types and cleanup/scoring utilities.
2. Extend the active import payload to include recovery items.
3. Update `StructuredUploadButton.tsx` to branch:
   - auto-apply on high-confidence-only imports
   - hold import and pass recovery state upward when low-confidence items exist
4. Add the minimal review panel in `ProfileReviewCard.tsx`, with `Import as-is`, `Cancel`, and capped review list behavior.
5. Apply review decisions back into sections, creating missing target sections when reassignment requires it, then continue the normal import flow.
6. Attach import recovery metadata to accepted/reassigned final blocks.
7. Add tests.

## Test Plan

### Unit

- cleanup utility normalizes bullets, glyphs, whitespace, and repeated breaks
- scoring utility marks weak/ambiguous sections as low confidence
- duplicate detection and unknown-section flagging

### Component

- `StructuredUploadButton` does not auto-apply when low-confidence items exist
- `ProfileReviewCard` shows low-confidence items only
- accept/reassign/ignore actions update state correctly
- reassignment can create a missing target canonical section safely
- `Import as-is` bypasses the review gate safely
- hard-cap behavior renders only the first `12` review items and summarizes the rest
- high-confidence imports still auto-apply without review

### Integration

- empty-state import: low-confidence blocks require review before `importCv(...)`
- existing-document import: low-confidence blocks require review before `reorderSections(...)`
- accepted/reassigned items land in the chosen section with `attributes.importRecovery`
- if review UI is bypassed with `Import as-is`, current import behavior still completes safely

## Product instrumentation

Step 1 should leave clear instrumentation hooks, even if analytics wiring is lightweight in the first implementation.

Track or make easy to track:

- import completion rate
- percentage of imports requiring manual review
- percentage of reviewed blocks resolved via accept / reassign / ignore
- early abandonment after import begins
- qualitative trust feedback from user testing or support notes

Implementation note:

- If full analytics is not already wired in this part of the app, Step 1 can emit structured console/debug events or lightweight callback points first, as long as the code leaves obvious places to connect real analytics next.

## Explicit Non-Goals for Step 1

- parser retraining or architecture rewrite
- full document diff/compare experience
- block-by-block drag-and-drop review workflow
- segmentation repair when parser unit boundaries are already wrong
- OCR retry, parser fallback orchestration, or structural reconstruction beyond the active pipeline
- automatic confidence tuning per parser provider/model
- broad legacy path unification (`useCvParser`, `UploadCvButton`, `StrictUploadButton`, old modal flows)

## Expected Step 1 Outcome

- Imported content can carry recovery metadata tied to blocks.
- Low-confidence imported blocks are surfaced before final import.
- Users can accept, reassign, or ignore uncertain blocks.
- Cleanup runs automatically.
- High-confidence imports keep the current behavior.
- The slice remains small, reversible, and compatible with the existing CvForge import pipeline.
- The product moves from `import -> messy editor` to `import -> normalize -> review uncertainty -> continue`, which is the trust improvement intended by Step 7.1.
