# TwoWeeks Product Roadmap

## Version 1.0

## Product design lead recommendation

## Objective: outperform funnel-first competitors without losing the long-term product advantage of the workspace/editor model

---

# 1. Executive summary

TwoWeeks already has the **better product foundation**:

* stronger workspace architecture
* stronger long-term editing model
* better proposal / job-context direction
* more premium visual system
* higher retention potential
* stronger defensibility if executed well

What it does **not** yet have is the same level of:

* first-run clarity
* import trust
* onboarding momentum
* AI consistency
* commercial packaging

That means the roadmap should **not** focus first on more features, more templates, or more aesthetic refinement.

It should focus first on the few systems that determine whether users:

1. understand the product quickly
2. trust it after import
3. get to first value fast
4. believe the AI is coherent
5. feel safe enough to export/pay
6. return for the next application

## Strategic product equation

The winning version of TwoWeeks is:

**ResumeLab’s activation discipline**
+
**TwoWeeks’ superior workspace/editor**
+
**TwoWeeks’ premium design system**
+
**job-aware proposal generation**
+
**reliable import**
+
**coherent AI**
===============

**category-leading application platform**

# 2. Product strategy

## Product thesis

TwoWeeks should become:

**the fastest way to turn a job post + your background into a premium, tailored application package**

That means the product must serve **two user modes**:

## Mode A — quick conversion user

This user wants:

* fast first result
* low friction
* low thinking
* quick export
* immediate reassurance

## Mode B — long-term companion user

This user wants:

* reusable resumes
* reusable proposal drafts
* multiple tailored versions
* structured editing
* job-specific adaptation
* strong AI in context
* document persistence

## Core strategy

Do not choose between funnel and editor.

### The right architecture is:

* **funnel shell for activation**
* **editor/workspace for ownership and retention**

That is the foundation of the roadmap.

# 3. Product design principles

These principles should guide every roadmap decision.

## Principle 1 — reduce fear before adding power

Users must quickly understand:

* what this product does
* where to start
* what it will do for them
* whether they can trust the output

## Principle 2 — the structured editor remains the source of truth

The skeleton editor is the right core model.
Do not switch to preview-first popup editing as the primary architecture.

Instead:

* keep structured editing
* strengthen live preview interaction
* make the relationship between source and output clearer

## Principle 3 — AI must feel like one product brain

All AI surfaces must feel coherent:

* job import AI
* proposal generation AI
* section rewrite AI
* floating toolbar AI
* import cleanup AI

If one is strong and another weak, users trust none of them.

## Principle 4 — templates are a confidence layer, not the workflow

Templates matter emotionally and commercially, but they should not dominate the editing experience.

## Principle 5 — premium visual quality must stay accessible

Design should feel:

* premium
* editorial
* trustworthy
* clear
* approachable

Not:

* elitist
* cryptic
* too “designer-only”

## Principle 6 — import trust matters as much as design quality

A beautiful product with unreliable import feels fake.

# 7. Phase 1 — Trust + activation

## Goal

Make the product easy enough to enter and trustworthy enough to continue.

This phase is the highest leverage phase. If it is not done, later improvements will not realize full value.

---

## 7.1 Initiative: Import recovery layer

### Problem

Resume import currently risks:

* wrong paragraph in wrong section
* weird glyphs
* broken bullets
* misassigned content
* hidden parser errors discovered too late

This damages trust immediately.

### Product decision

Do not rely only on better parsing.
Build a **recovery UX** around parsing.

### Deliverables

* import normalization pass
* glyph cleanup pass
* duplicate text cleanup
* bullet normalization
* confidence scoring on imported blocks
* “review uncertain blocks” screen before full document entry
* quick reassignment UI for uncertain content
* obvious section repair flow

### UX behavior

Instead of:

* import → drop user into editor with messy result

Do:

* import → normalize → surface uncertain areas → quick review → continue

### Example user-facing language

* “We imported your resume. Review 3 uncertain sections before continuing.”
* “We’re not sure where this paragraph belongs.”
* “We found unusual formatting in this section.”

### Success metrics

* import completion rate
* % imports requiring manual review
* % reviewed blocks successfully resolved
* reduction in early abandonment after import
* qualitative trust signal in user testing

### Why this is Phase 1

Because this is not a polish problem. It is a trust gateway.

---

## 7.2 Initiative: Quick-start guided path

### Problem

A pure editor is stronger long-term, but weaker for cold-start conversion.

### Product decision

Build a **short guided entry flow** that produces a first draft quickly, then routes into the editor.

### Deliverables

* “What do you want to create?” entry screen
* short creation path for:

  * Resume
  * Cover letter / Proposal
  * Resume + proposal
  * Import existing resume
* job import / paste job post step
* tone selection step
* first draft generation step
* handoff into editor

### Recommended flow

1. Choose output
2. Import resume or start from profile
3. Import job or skip
4. Choose tone
5. Generate draft
6. Open in structured editor

### UX principle

This must feel:

* fast
* premium
* not over-explained
* not like a long ResumeLab clone

### Success metrics

* time to first draft
* % users reaching editor
* % users completing first draft from landing
* % users continuing after draft generation
* paid conversion from quick-start path

---

## 7.3 Initiative: AI interaction rulebook

### Problem

AI behaves differently across:

* proposal generation
* floating toolbar
* section-level edits
* import cleanup

That inconsistency weakens trust.

### Product decision

Define and enforce a **single AI interaction framework**.

### Deliverables

A product-wide AI behavior spec covering:

#### Single-result actions

Use for:

* Fix grammar
* Shorten
* Simplify
* Formalize
* Tighten

#### Recommended-result + optional alternatives

Use for:

* Rewrite experience bullets
* Rewrite summary
* Rewrite proposal paragraph
* Tailor text to job

Default:

* 1 recommended version
* optional 2 alternatives max

#### Open-ended AI mode

Use only for:

* Ask AI
* custom instruction
* advanced user intent

### Required controls

Every AI action should support:

* Replace
* Insert below
* Keep both
* Undo

For high-value rewrites:

* optionally show diff/highlight
* optionally label variants:

  * More concise
  * More formal
  * Stronger impact

### Success metrics

* AI accept rate
* undo rate after AI changes
* “show alternatives” usage
* satisfaction with rewrite outcomes
* consistency perception in usability testing

---

## 7.4 Initiative: Editor ↔ preview linking

### Problem

The skeleton editor is correct structurally, but some users may still feel detached from the final output.

### Product decision

Keep the skeleton editor, but make preview interaction much stronger.

### Deliverables

* hover section in editor → highlight matching preview block
* click preview block → focus or scroll to corresponding section
* active section indicator in both panes
* smooth section sync
* optional section focus mode

### UX principle

The user should feel:
**“I’m editing the real document”**
without making preview the primary source of truth.

### Success metrics

* section edit completion
* reduced confusion in usability testing
* higher task success in first session
* longer editing depth per session

# 8. Phase 2 — Quality + coherence

## Goal

Make the product feel category-leading inside the editor and clearly valuable enough to pay for.

---

## 8.1 Initiative: First-run onboarding system

### Problem

The product is under-explained for first-time users, but a long tutorial would be the wrong fix.

### Product decision

Build **progressive onboarding**, not a giant tooltip tour.

### Deliverables

* first-session checklist
* contextual helper cards
* empty-state guidance
* 1–2 spotlight interactions only for critical actions
* dismissible onboarding state

### Checklist example

* Import your resume
* Import a job
* Generate your first proposal
* Improve one section with AI
* Export your document

### UX principle

Teach through progress, not through lectures.

### Success metrics

* first-session task completion
* feature discovery
* drop-off between first and second key actions
* checklist completion rate

---

## 8.2 Initiative: Document health / readiness layer

### Problem

Users need help knowing whether a document is actually ready to send.

### Product decision

Add a **readiness layer** rather than a vague gamified score.

### Deliverables

#### Resume readiness

* contact info completeness
* summary strength flag
* unresolved import issues
* weak skill coverage
* repeated verbs
* export readiness

#### Proposal readiness

* missing recipient details
* missing company/job alignment
* unresolved placeholders
* weak call to action
* low keyword alignment
* incomplete header lines
* export readiness

### UI form

* checklist panel
* green/amber/red state
* direct “Fix this” actions

### Success metrics

* export confidence
* reduced abandonment before export
* reduced support complaints
* increased quality perception in tests

---

## 8.3 Initiative: Focused template switcher

### Problem

Templates matter emotionally, but a giant gallery harms focus.

### Product decision

Build a **controlled template switcher**.

### Deliverables

* current template visible by default
* “Change template” action
* drawer or modal switcher
* curated set of 6–12 templates
* strong labels such as:

  * Classic
  * Modern
  * ATS-safe
  * Compact
  * Executive
  * Editorial

### UX principle

Templates are a confidence layer, not the core task.

### Success metrics

* template switch usage
* time spent browsing vs editing
* satisfaction with output style
* paid conversion impact if premium templates are gated

---

## 8.4 Initiative: Extension-to-app handoff refinement

### Problem

The LinkedIn extension is strategically valuable, but the handoff must feel seamless and purposeful.

### Product decision

Treat the extension as a first-class acquisition and workflow channel.

### Deliverables

Extension actions:

* Save job
* Tailor resume
* Generate proposal

In-app handoff:

* imported job lands as a clean object
* extracted role/company/keywords visible immediately
* suggested next action appears immediately

### UX principle

One-click import must create momentum, not an extra setup burden.

### Success metrics

* extension activation rate
* successful handoff rate
* % imported jobs leading to a draft
* retention among extension users

---

## 8.5 Initiative: Premium value packaging

### Problem

A better product can still under-convert if premium value is not clearly framed.

### Product decision

Clarify why TwoWeeks is worth paying for.

### Deliverables

Clear premium value architecture:

* unlimited tailoring
* advanced AI rewriting
* premium templates
* proposal generation
* saved jobs
* duplicate and retarget workflows
* multi-document workspace
* export flexibility
* extension benefits

### UX principle

Do not make the product feel like “pay to export a PDF.”
Make it feel like “pay for professional leverage.”

### Success metrics

* paywall conversion
* plan selection rate
* premium feature click-through
* conversion lift after message improvements

---

## 8.6 Initiative: Proposal naming and framing clarity

### Problem

“Proposal” may be strategically smart but can confuse mainstream users.

### Product decision

Use clearer transitional framing.

### Recommendation

For now:

* **Cover letter / Proposal**
  or
* **Application Letter**

Keep “proposal” if you want it internally, but do not force users to decode it.

### Success metrics

* start rate for proposal flow
* user comprehension in tests
* confusion reduction in first-run sessions

# 9. Phase 3 — Retention + system moat

## Goal

Turn TwoWeeks from a strong editor into a real job-application workspace.

---

## 9.1 Initiative: Jobs as first-class object

### Problem

Right now jobs are imported context, but not yet clearly a durable system object.

### Product decision

Build a true Jobs layer.

### Deliverables

Job object with:

* title
* company
* source URL
* raw description
* extracted keywords
* extracted responsibilities
* seniority
* location
* tone cues
* linked resume variants
* linked proposals

### UX value

This creates:

* memory
* reuse
* stronger document linking
* stronger retention
* stronger moat

### Success metrics

* jobs per user
* documents linked to jobs
* return rate via saved jobs
* repeat proposal generation

---

## 9.2 Initiative: Duplicate / retarget workflow

### Problem

Users applying to multiple roles need fast reuse, not repeated full drafting.

### Product decision

Make retargeting a first-class workflow.

### Deliverables

* duplicate resume for job
* duplicate proposal for job
* “retarget to new role” flow
* linked source document awareness
* template-preserving duplication
* job-linked variant naming

### UX principle

Tailoring should feel much faster than creating from scratch.

### Success metrics

* duplicates per user
* retarget flow usage
* average documents per user
* repeat session rate

---

## 9.3 Initiative: Versioning / compare states

### Problem

Users need confidence when revising strong documents.

### Product decision

Add lightweight versioning and compare.

### Deliverables

* save version snapshots
* compare current vs previous
* restore prior version
* version labels by job or date

### Success metrics

* version restore rate
* longer edit session confidence
* lower fear of AI overwrite
* more experimentation

---

## 9.4 Initiative: Advanced tone system under the hood

### Problem

The visible tone system should stay simple, but the writing system needs more nuance.

### Product decision

Keep 3 top-level tones:

* Balanced
* Warm
* Formal

Add internal modifiers:

* concise
* assertive
* executive
* ATS-focused
* plain language
* achievement-heavy

These should be used by:

* AI generation
* advanced mode
* maybe hidden defaults from job type

### Success metrics

* tone satisfaction
* lower confusion at tone selection
* improved output quality consistency

# 13. What not to do

These are the mistakes I would actively block.

## Do not:

* replace the skeleton editor with preview-first popup editing
* add too many tone options
* build a giant template gallery now
* rely on a big onboarding tour
* treat parsing as a backend-only problem
* let AI behave differently in every surface
* market premium design without reassurance and clarity
* overinvest in landing before fixing import and activation

# 15. Final recommendation

If I were acting as product design lead, I would say:

**TwoWeeks should not become a prettier ResumeLab.**
It should become:

* easier to start than it is now
* more trustworthy on import
* more coherent in AI behavior
* more emotionally legible in editing
* more commercially explicit
* and far stronger than ResumeLab once users go beyond the first draft

That is the winning move.

## Final product goal

**A guided-but-powerful application workspace where users can import a job, import their background, generate a high-quality draft fast, and refine it in a premium structured editor that stays useful throughout the full job search.**
