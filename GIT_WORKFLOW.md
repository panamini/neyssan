# Git Workflow and Branching Strategy

This document outlines the standard process for contributing to this repository. Following this workflow will prevent merge conflicts, ensure code quality, and maintain a clean, understandable history.

## The Core Principles

1.  **`main` is the Source of Truth:** The `main` branch is considered sacred. It should always be in a stable, deployable state. No one should ever push directly to `main`.
2.  **One Feature, One Branch:** All new work, including features, bugfixes, and chores, must be done on a dedicated branch.
3.  **All Work Goes Through a Pull Request:** All changes must be reviewed and approved via a Pull Request (PR) before being merged into `main`.

---

## The Standard Workflow

This is the step-by-step process for all development work.

### 1. Start Your Work: Create a New Branch from `main`

Before starting anything new, ensure you have the latest version of the `main` branch and create a new branch from it.

```bash
# 1. Switch to your local main branch
git checkout main

# 2. Pull the latest changes from the server
git pull origin main

# 3. Create your new, clearly named branch
git checkout -b feat/my-new-feature
```

**Branch Naming Conventions:**

Use a consistent prefix to indicate the type of work:
*   `feat/`: For a new feature (e.g., `feat/add-user-avatars`)
*   `fix/`: For a bug fix (e.g., `fix/login-page-crash`)
*   `chore/`: For maintenance tasks (e.g., `chore/update-dependencies`)

### 2. Do Your Work: Commit Changes

Make your code changes on your feature branch. Commit your work early and often with clear, descriptive messages.

```bash
# Stage your changes
git add .

# Commit with a clear message
git commit -m "feat: Add avatar component to user profile page"
```

### 3. Share Your Work: Open a Pull Request

When your feature is complete and tested, push your branch to the remote repository and open a Pull Request (PR) on GitHub.

```bash
# Push your branch to the remote repository
git push -u origin feat/my-new-feature
```

Navigate to the repository on GitHub. You will see a prompt to create a new Pull Request from your branch.

*   **Target Branch:** Ensure the PR is targeting the `main` branch.
*   **Title and Description:** Write a clear title and a detailed description of the changes you made.

### 4. Finish Your Work: Merge and Cleanup

Once the PR has been reviewed, approved, and all automated checks have passed, it can be merged into `main` using the GitHub UI.

*   **Merge the PR:** Use the "Squash and merge" or "Rebase and merge" option for a clean history.
*   **Delete the Branch:** After merging, delete your feature branch. GitHub provides a button for this, or you can do it locally:
    ```bash
    # Switch back to main
    git checkout main

    # Delete the local feature branch
    git branch -d feat/my-new-feature
    ```

## Important Rule: Ignoring Generated Code

The `convex/_generated` directory contains code that is automatically generated by the Convex framework. To prevent constant, meaningless merge conflicts, this directory is listed in the `.gitignore` file.
